## الجزء 4 — خطة الإصلاح للمنفّذ

### 4.0 قواعد صارمة (أي مخالفة = إيقاف فوري وتقرير)
1. اقرأ `AGENTS.md` ثم `docs/FINANCE_LAW.md` كاملاً قبل أي تعديل. القانون أعلى من الكود.
2. لا تعديل لأي ملف قديم في `supabase/migrations/`. كل تغيير SQL = ملف هجرة **جديد** بتاريخ أحدث، ونسخ الدالة كاملة من آخر تعريف ثم تغيير السطر المطلوب فقط.
3. لا SQL كتابة ولا هجرة على القاعدة الحية بدون موافقة المالك الصريحة في المحادثة نفسها. القراءة (SELECT) مسموحة.
4. ممنوع: حذف بيانات، `deleteDatabase`، `localStorage.clear()`، تعديل `Warehouses.tsx` / `StockTransfer.tsx` / `warehouses-cloud.ts`، تغيير نصوص أزرار قائمة، كتابة كلمات مرور أو مفاتيح في الملفات، `push --force`، `--no-verify`، وضع اسم أي نموذج في الإيداعات.
5. كل إصلاح مالي يحتاج **اختباراً على كود الإنتاج** (حالة ذهبية في `supabase/tests/golden/scenarios.mjs` لـ SQL، أو اختبار `tsx` في `src/lib/__tests__/` مسجّل في `scripts/finance-check.mjs` لكود التطبيق).
6. لا تُضعف اختباراً ولا تغيّر قيمة متوقعة لتنجح.
7. P-5 لا يُنفَّذ قبل قرار المالك (شامل أم صافٍ).
8. إضافة ملف أو تصدير جديد = تحديث `scripts/map-descriptions.json` ثم `npm run maps`.

### 4.1 الطريقة المرجعية للتحقق (تُنفَّذ بعد كل إصلاح، بالترتيب)
```
V1  npm ci                                   (مرة واحدة)
V2  npm run finance:sql      → يجب: "FINANCE SQL GATE: GREEN"
V3  npm run finance:check    → يجب: "FINANCE GATE: GREEN"
V4  npx tsc --noEmit -p tsconfig.app.json   → يجب: لا أخطاء جديدة (اليوم: 0)
V5  npm run maps && npm run maps:check       → يجب: "all N maps up to date"
V6  npm run build                            → يجب: exit 0
V7  (عند تغيير SQL) طبّق الهجرة حياً بعد موافقة المالك، ثم:
    npm run db:drift-sql > drift.sql ; شغّل drift.sql على القاعدة الحية
    → يجب: لا صف مالي جديد (المسموح فقط بنود P-8 حتى تُغلق)
V8  (عند تغيير SQL أو مسار مال) شغّل supabase/tests/finance_reconcile_readonly.sql على الحية
    → يجب: R-01..R-09 كلها 0
```

**حلقة التكرار:** إصلاح ← V2..V8 ← إن فشل أي بند: أصلح وأعد من V2. **نفس البند يفشل 3 مرات متتالية = توقف** وارفع تقريراً بالمخرجات الحقيقية، وأرجع التعديل غير الناجح.

### 4.2 مهام الإصلاح

#### T-1 (P-2 + P-1) رصيد العميل: معرّف عملية ثابت + طابور بلا اتصال
- **الملفات:** `src/lib/cloud/customer-credit-cloud.ts`، `src/components/customers/CustomerCreditDialog.tsx`، `src/lib/sync-queue.ts`، `src/lib/cloud/sync-operation-processor.ts`.
- **المطلوب:**
  1. المعرّف يُولَّد **مرة واحدة** عند فتح العملية في الواجهة ويُمرَّر للدالة، ويُعاد استخدامه عند إعادة المحاولة (لا `randomUUID()` داخل الدالة).
  2. بلا اتصال: تُضاف العملية للطابور (`addUniqueOperation`) بنفس المعرّف، وتُعاد عند الاتصال. الخادم أصلاً يعيد نفس النتيجة لنفس المعرّف.
  3. الصرف النقدي: حركة الدرج المحلية تُسجَّل مرة واحدة فقط، ولا تتكرر عند إعادة الإرسال.
- **اختبار القبول:** اختبار `tsx` جديد يثبت: (أ) استدعاءان بنفس المعرّف = عملية واحدة في الطابور؛ (ب) بلا اتصال تُطابَر ولا ترمي خطأ؛ (ج) الصرف يخصم الدرج المحلي مرة واحدة. + حالة ذهبية: إعادة `payout_store_credit_atomic` و`apply_store_credit_to_debt_atomic` بنفس المعرّف لا تكرر (موجودة جزئياً في C12؛ أضف apply).

#### T-2 (P-3 + P-4) العرض والدقة
- **ملف هجرة جديد:** ينشئ `customer_credit_balances` بنفس التعريف الحي مع `security_invoker=true`، ويغيّر التقريب في العرض وفي `issue_store_credit_atomic` و`payout_store_credit_atomic` من 4 إلى 8 منازل.
- **تحذير مالي:** تغيير الدقة تغيير سلوك مالي (القانون F-02 يؤيده)، لكنه يحتاج موافقة المالك قبل التطبيق الحي.
- **اختبار القبول:** حالة ذهبية: إصدار 1.23456789 ثم قراءة العرض = 1.23456789؛ صرف نفس المبلغ يترك الرصيد 0 بالضبط.
- **التحقق:** V7 يجب أن يُظهر أن `customer_credit_balances` لم يعد "ONLY_LIVE".

#### T-3 (P-8) مزامنة غير المالي
- ملف هجرة جديد يحتوي **نسخة مطابقة** من التعريفات الحية: `boss_activate_license`، دوال push tokens وجداولها، أعمدة ومشغّل `app_broadcasts` و`support_messages`. التعريف يُقرأ حياً بـ `pg_get_functiondef` / `information_schema`.
- **القبول:** V7 = صفر صفوف.

#### T-4 (P-5) بعد قرار المالك فقط
- إن اختار "شامل": تقارير المبيعات والكاشير تعرض `total` (شامل)، وتقرير الضريبة يبقى يفصل الضريبة.
- **القبول:** على نفس البيانات، كل التقارير تعطي نفس "إجمالي المبيعات" لنفس اليوم (مقارنة شاشة بـ `sum(invoices.total)`).

#### T-5 (P-6, P-9, P-10) واجهة
- P-10: رسالة الرفض تشرح أن الحركة الأصلية غير موجودة وماذا يفعل المستخدم (مفتاح ترجمة جديد في اللغات الخمس، بلا تغيير منطق).
- P-6 وP-9: **تحتاج موافقة المالك** (قفل الواجهة).

#### T-6 اختبارات لم تُنفَّذ
K-06، K-07، J-04، J-08، J-09، D-10، L. كل حالة: تنفيذ من الواجهة (Playwright، حساب الاختبار فقط) ثم مقارنة بـ SELECT. ممنوع إنشاء بيانات على حساب غير حساب الاختبار.

### 4.3 التسليم
**إن كان لدى المنفّذ صلاحية GitHub:**
1. فرع جانبي `ai/<topic>` (أو الفرع المحدد للجلسة)، إيداع لكل مهمة برسالة إنجليزية واضحة.

**إن لم يكن لديه صلاحية GitHub:**
1. ملف ZIP يحتوي **فقط** الملفات المعدّلة/الجديدة بنفس مساراتها في المستودع.

3. **يُفحص أولاً:** المراجع يفك الـ ZIP على نسخة نظيفة من `main`، يشغّل V1..V6 بنفسه، ويقرأ كل هجرة. فقط بعد نجاح كل البنود تُطبَّق الهجرات حياً (بموافقة المالك) ويُشغَّل V7..V8، ثم يُدفع.
